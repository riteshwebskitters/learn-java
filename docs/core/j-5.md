2. J-0 --- Java program basics and execution

Topics covered
Class and file basics
- A Java program is organized around classes.
- A source file containing a public class must use the matching
  filename. For example, public class HelloWorld belongs in
  HelloWorld.java.
- The class provides a structure in which methods and fields can be
  declared.
The main method
public static void main(String[] args) {
    System.out.println("Hello Java");
}
Discussed: - public: the method can be accessed by the Java runtime. -
static: the method can be called without first creating an object of
the class. - void: the method does not return a value. - main: the
conventional entry point for a standard Java application. -
String[] args: an array of command-line arguments supplied when the
program starts.
Compile and run
javac HelloWorld.java
java HelloWorld
- javac compiles Java source code.
- java launches the compiled class.
- Compilation and execution are separate steps in this workflow.
Printing
- System.out.print() prints without automatically moving to a new
  line.
- System.out.println() prints and then moves to a new line.

Stack, heap, and references
Discussed the conceptual difference between: - Local variables and
method-call frames, commonly associated with stack memory. - Objects
created with new, which are stored on the heap. - A reference
variable, which holds a reference to an object rather than containing
the object itself.

Practised the distinction between: - Copying a primitive value. -
Copying an object reference. - Mutating an object through a reference. -
Reassigning a reference to another object.

These are foundational mental models; actual JVM memory management is
more nuanced than a simple "all locals on stack, all objects on heap"
rule.
final
- final prevents a variable from being assigned a new value after
  initialization.
- For a reference variable, final prevents reassignment of the
  reference; it does not automatically make the referenced object
  immutable.
Scope
- A variable is available only within the scope in which it is
  declared.
- Local variables declared inside a method or block cannot be accessed
  outside that scope.
Type casting
- Discussed converting values between compatible types.
- Widening conversions can often happen automatically.
- Narrowing conversions may require an explicit cast and can lose
  information.
User input with Scanner
Created UserInput.java to read a name, age, and city from the
terminal.

Example:
Scanner scanner = new Scanner(System.in);

String name = scanner.nextLine();
int age = scanner.nextInt();
scanner.nextLine(); // consume the pending newline
String city = scanner.nextLine();
Important Scanner behaviour: - nextInt() reads the integer token but
does not consume the line break after it. - A following nextLine() may
consume the remaining newline and appear to skip input. - Calling
nextLine() after nextInt() consumes that pending line break.

Also corrected a common entry-point mistake:

A key problem-solving lesson was to identify the business rules before

Validation order
A typical withdrawal flow needs to establish: 1. The account is valid /
exists. 2. The account is active and eligible. 3. The requested amount
is valid and positive. 4. The balance is sufficient. 5. The balance is
updated only after the checks pass.

The exact rules can vary by application, but validation should happen
before changing the balance.
switch
Practised switch as an alternative to long if / else if chains
when selecting among discrete cases, such as transaction types.

Covered: - Matching a case. - default when no case matches. -
Returning or selecting a fallback value such as -1 in a practice
example. - Choosing switch when a value is being compared against a
known set of alternatives.
Transaction design questions
Explored the difference between transaction types such as withdrawal,
transfer, and refund. A refund is not simply a withdrawal with a
negative amount: it represents a different business operation and should
be modelled explicitly. The direction of money movement and the
validation rules depend on the transaction type.
5. J-4 --- Loops and nested-loop pattern practice
Loop types covered
- for
- while
- do while
- Nested loops
- break
- continue
for loop
Used when the number of iterations or the iteration range is known or
controlled by a counter.

General structure:
for (int i = 1; i <= 5; i++) {
    System.out.println(i);
}
while loop
- Checks its condition before each iteration.
- May execute zero times if the condition is initially false.
do while loop
- Executes its body once before checking the condition.
- Therefore, it executes at least once.
break and continue
- break exits the nearest enclosing loop.
- continue skips the remaining statements in the current iteration
  and proceeds to the next iteration.
Practised these ideas in a transaction-attempt example: - A loop tracked
attempts. - continue skipped a selected iteration. - break stopped
processing when a stopping condition was reached.
Nested loops
A loop inside another loop is a nested loop.

Key execution rule: - For each iteration of the outer loop, the inner
loop runs through its complete range unless it is interrupted. - The
outer loop then advances and the inner loop starts again.
Pattern exercises
Practised: - A square star pattern. - A right-angled triangle. - An
inverted triangle. - Dry-running the values of i and j. - Counting
how many times the inner loop executes for a particular outer-loop
iteration.

Example of the corrected triangle logic:
int rows = 5;

for (int i = 1; i <= rows; i++) {
    for (int j = 1; j <= i; j++) {
        System.out.print("*");
    }
    System.out.println();
}
Expected shape:
*
**
***
****
*****
The newline belongs after the inner loop so that each outer-loop
iteration produces one row.

Declaration versus invocation
Declaring a method defines what it does. It does not run automatically.
The method executes when it is invoked (called).
public static void displayMessage() {
    System.out.println("Hello");
}

// Calling it:
displayMessage();
Parameters versus arguments
- Parameter: the variable declared in a method definition.
- Argument: the actual value supplied when calling the method.
public static int calculateDeposit(int amount, int balance) {
    return amount + balance;
}

// `amount` and `balance` are parameters.
// `1500` and `2500` are arguments.
int updatedBalance = calculateDeposit(1500, 2500);
Return types: void versus a value
- void means the method does not return a value to its caller.
- A method with a return type such as int must return a compatible
  value on every valid execution path.
- Printing a value is not the same as returning it.
- A returned value can be stored in a variable, passed to another
  method, or used in an expression.
Example:
public static int calculateDeposit(int amount, int balance) {
    return amount + balance;
}
Separating calculation from display
The user first created a method that calculated the balance internally
and another method that displayed it. We then refactored the design so
the calculation and display responsibilities were separate.

Refactored example:
public class Concepts {
    public static int calculateDeposit(int amount, int balance) {
        return amount + balance;
    }

    public static void displayBalance(int balance) {
        System.out.println("Updated wallet balance: " + balance);
    }

    public static void main(String[] args) {
        int balance = calculateDeposit(1500, 5500);
        displayBalance(balance);
    }
}
The example returns 7000.

Design lesson: - calculateDeposit() calculates and returns a result. -
displayBalance() displays a value it receives. - main() coordinates
the calls. - A display method should not need to repeat or own the
calculation when that calculation is a separate responsibility.
Method composition
A returned value can be passed directly into another method:
displayBalance(calculateDeposit(5000, 2000));
This is valid, although storing the intermediate result in a clearly
named variable can make more complex flows easier to read and debug.
Method overloading
Method overloading means declaring multiple methods with the same name
but different parameter lists.

Valid differences include: - Different number of parameters. - Different
parameter types. - Different parameter order (when the resulting type
sequence differs).

Example:
public static int calculateDeposit(int amount, int balance) {
    return amount + balance;
}

public static int calculateDeposit(int amount, int balance, int bonus) {
    return amount + balance + bonus;
}
The user implemented this two-argument / three-argument overload
successfully. The three-argument example
calculateDeposit(1500, 5500, 800) returns 7800.

Important rules: - Java selects an overload using the method name and
parameter types/order at compile time. - Parameter variable names do not
make overloads different. - Return type alone cannot distinguish
overloaded methods. - Two methods with exactly the same name and
parameter types/order cannot be declared as separate overloads.
Problem decomposition: wallet withdrawal
A larger operation should be divided into methods with clear
responsibilities.

The exercise introduced these roles: - processWithdrawal() ---
coordinates the operation. - validateAccount() --- checks whether the
supplied account identity is valid. - validateAmount() --- checks
whether the withdrawal amount is positive. - checkBalance() --- checks
whether enough funds are available. - deductBalance() --- calculates
the resulting balance. - displayBalance() --- displays the result.

A refactored practice design was:
public class WalletWithdrawal {
    public static boolean validateAccount(String userAccountNumber, String accountNumber) {
        return userAccountNumber != null && userAccountNumber.equals(accountNumber);
    }

    public static boolean validateAmount(int withdrawalAmount) {
        return withdrawalAmount > 0;
    }

    public static boolean checkBalance(int balance, int withdrawalAmount) {
        return balance >= withdrawalAmount;
    }

    public static int deductBalance(int balance, int withdrawalAmount) {
        return balance - withdrawalAmount;
    }

    public static void displayBalance(int updatedBalance) {
        System.out.println("Your available balance: " + updatedBalance);
    }

    public static void processWithdrawal(
            String userAccountNumber,
            String accountNumber,
            int balance,
            int withdrawalAmount
    ) {
        if (!validateAccount(userAccountNumber, accountNumber)) {
            System.out.println("Account does not exist");
            return;
        }

        if (!validateAmount(withdrawalAmount)) {
            System.out.println("Invalid withdrawal amount");
            return;
        }

        if (!checkBalance(balance, withdrawalAmount)) {
            System.out.println("Insufficient funds");
            return;
        }

        int updatedBalance = deductBalance(balance, withdrawalAmount);
        System.out.println("Withdrawal successful");
        displayBalance(updatedBalance);
    }

    public static void main(String[] args) {
        String userAccountNumber = "ABC147";
        String accountNumber = "ABC147";
        int balance = 5000;
        int withdrawalAmount = 1500;

        processWithdrawal(userAccountNumber, accountNumber, balance, withdrawalAmount);
    }
}
For the sample input, the expected output is:
Withdrawal successful
Your available balance: 3500
Test cases discussed: | Starting balance | Withdrawal amount |
Expected outcome | |---:|---:|---| | 5000 | 1500 | Success;
resulting balance 3500 | | 5000 | -1500 | Invalid amount | | 5000
| 0 | Invalid amount | | 5000 | 6000 | Insufficient funds | |
5000 | 5000 | Success; resulting balance 0 |
Design lessons from the withdrawal exercise
- Do not mix unrelated validation responsibilities. validateAmount()
  checks the amount itself; checkBalance() checks the relationship
  between amount and balance.
- A method should receive the data it needs rather than silently
  creating unrelated local test data.
- processWithdrawal() acts as an orchestrator: it calls the smaller
  methods in the correct business order.
- Validate before changing the balance.
- Use guard clauses / early returns to stop processing when a
  prerequisite fails.
- ! negates a boolean condition.
- && uses short-circuit evaluation: the right-hand expression is
  evaluated only if the left-hand expression is true.
- Account existence/identity and account active status are different
  business checks. They should not be treated as interchangeable.
- A negative withdrawal amount must not be allowed to increase the
  wallet balance accidentally.
- A void coordinator is suitable for this exercise because its
  caller does not currently need a returned result. A larger
  application might instead return a transaction result, status, or
  domain object.

7. Clean-code habits and problem-solving principles covered so far
These principles have appeared repeatedly in the exercises:
1. Understand the requirement before coding. Identify the inputs,
   business rules, expected outcomes, and failure cases.
2. Plan the execution flow. Work out the order of checks and
   operations before writing nested conditions.
3. Give methods one clear responsibility. Avoid mixing validation,
   calculation, input, and display when they can be separated cleanly.
4. Use meaningful names. Names such as withdrawalAmount,
   updatedBalance, and validateAmount communicate intent better
   than vague names.
5. Pass required data through parameters. Avoid hiding important
   inputs inside methods.
6. Return calculation results. Keep calculation methods reusable;
   let a separate caller decide what to do with the result.
7. Validate before mutation. Do not update a balance until the
   operation has passed its required checks.
8. Use guard clauses where appropriate. Handle invalid cases early
   to keep the successful path readable.
9. Dry-run loops and conditions. Track variable values step by step
   rather than guessing the output.
10. Test edge cases. Include zero, negative values, exact balance,
    insufficient balance, and invalid account details.
11. Understand why code works. Do not treat a compiling program as
    proof that its business logic is correct.

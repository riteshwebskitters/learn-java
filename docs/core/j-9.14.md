J-9.14 — Records (record)
1. Why do we need records?
Imagine we want to represent a transaction receipt.

Using a regular Java class, we'd typically need to write:
- Fields
- Constructor
- Getters
- toString()
- equals()
- hashCode()
That's a lot of repetitive code for something whose main purpose is simply to hold data.

Java introduced records to make data-carrier classes much simpler.
2. First working demonstration
Create TransactionReceipt.java inside corejava/oop.

package corejava.oop;

public record TransactionReceipt(
    String transactionId,
    double amount,
    TransactionStatus status
) {
}



That's it. No manually written constructor or getters!

Now test it in BankAccountDemo.java:

TransactionReceipt receipt = new TransactionReceipt(
    "TXN1001",
    2500.00,
    TransactionStatus.SUCCESS
);

System.out.println(receipt);

System.out.println("Transaction ID: " + receipt.transactionId());
System.out.println("Amount: " + receipt.amount());
System.out.println("Status: " + receipt.status());



Expected output:
TransactionReceipt[transactionId=TXN1001, amount=2500.0, status=SUCCESS]
Transaction ID: TXN1001
Amount: 2500.0
Status: SUCCESS


3. What does Java generate automatically?
For this record:
public record TransactionReceipt(
    String transactionId,
    double amount,
    TransactionStatus status
) {}


Java automatically provides:
Generated member	Purpose
Constructor	Initializes all components
transactionId()	Returns transaction ID
amount()	Returns amount
status()	Returns status
toString()	Provides readable object representation
equals()	Compares record values
hashCode()	Generates a hash based on record values

Notice that record accessors don't use the conventional getTransactionId() naming.
4. Important: Records are immutable data carriers
Consider:
receipt.amount = 5000; // Compilation error


You cannot reassign a record component.

Record components are implicitly private final.

However, remember that this is shallow immutability: if a record contains a mutable object, that object's internal state may still change.
5. Can records contain methods?
Yes!
public record TransactionReceipt(
    String transactionId,
    double amount,
    TransactionStatus status
) {
    public boolean isSuccessful() {
        return status == TransactionStatus.SUCCESS;
    }
}


Usage:
System.out.println(receipt.isSuccessful());


Records can also have validation in their constructors, which we'll explore when we cover exception handling.

6. Regular class vs record
Feature	Regular class	Record
Fields	Manually declared	Declared in record header
Constructor	Usually written manually	Generated
Accessors	Usually written manually	Generated
toString()	Usually overridden manually	Generated
equals()	Default identity comparison unless overridden	Generated value comparison
Mutability	Depends on implementation	Components are final
Inheritance	Can extend a class	Cannot extend another class

A record can still implement interfaces.

Practical rule: Use a regular class when an object has identity, mutable state or complex lifecycle behaviour. Use a record when its primary responsibility is carrying data.

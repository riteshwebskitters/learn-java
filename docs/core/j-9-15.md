J-9.15 — toString(), equals() and hashCode()
These three methods come from Java's Object class. Every Java class inherits them, even if you never explicitly extend Object.

They solve three practical problems:
Method	What it answers
toString()	How should this object be represented as text?
equals()	Are these two objects considered equal?
hashCode()	What hash value represents this object for hash-based collections?

1. toString() — How do we display an object?
Let's use a simple class:
public class Customer {
    private String name;
    private String city;

    public Customer(String name, String city) {
        this.name = name;
        this.city = city;
    }
}


Now create an object:
Customer customer = new Customer("Ritesh", "Kolkata");

System.out.println(customer);


You might expect something like:
Customer[name=Ritesh, city=Kolkata]


But without overriding toString(), Java produces something similar to:
Customer@5acf9800


Why?

Because the inherited Object.toString() implementation doesn't know how you want your customer details displayed.

We can override it:
@Override
public String toString() {
    return "Customer{name='" + name + "', city='" + city + "'}";
}


Now:
System.out.println(customer);


Output:
Customer{name='Ritesh', city='Kolkata'}


Important: System.out.println(customer) automatically calls customer.toString() when the argument is an object.
2. equals() — Are two objects equal?
Consider this:
Customer customer1 = new Customer("Ritesh", "Kolkata");
Customer customer2 = new Customer("Ritesh", "Kolkata");

System.out.println(customer1 == customer2);
System.out.println(customer1.equals(customer2));


Both objects contain the same data, but they are two separately created objects.
Two different objects
customer1

name: Ritesh

city: Kolkata
Object A


customer2

name: Ritesh

city: Kolkata
Object B



Same field values, different object identities.

The difference:
- == checks whether both references point to the exact same object.
- equals() checks equality according to the class's implementation.
By default, Object.equals() also checks object identity. So both expressions above return false.

But suppose our business rule says two customers are equal when their names and cities match.

We can override equals():
@Override
public boolean equals(Object obj) {
    if (this == obj) {
        return true;
    }

    if (!(obj instanceof Customer other)) {
        return false;
    }

    return name.equals(other.name)
            && city.equals(other.city);
}


Now customer1.equals(customer2) returns true.

A few important details:
- this == obj: same object, so immediately equal.
- instanceof Customer other: checks the type and gives us a Customer reference.
- The final return compares the actual data.
3. hashCode() — Why does it matter?
Imagine you want to store customers in a HashSet or use them as keys in a HashMap.

Java uses hashCode() to help locate objects efficiently.

The most important contract is:

If two objects are equal according to equals(), they must have the same hashCode().

So, if we override equals(), we should also override hashCode().

For our Customer class:
@Override
public int hashCode() {
    return Objects.hash(name, city);
}


Add this import:
import java.util.Objects;


Now our class has all three methods:
import java.util.Objects;

public class Customer {
    private String name;
    private String city;

    public Customer(String name, String city) {
        this.name = name;
        this.city = city;
    }

    @Override
    public String toString() {
        return "Customer{name='" + name + "', city='" + city + "'}";
    }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) {
            return true;
        }

        if (!(obj instanceof Customer other)) {
            return false;
        }

        return Objects.equals(name, other.name)
                && Objects.equals(city, other.city);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, city);
    }
}


4. How records relate to this
Remember our PaymentDetails record?
public record PaymentDetails(
        String paymentId,
        double amount,
        String paymentMethod,
        TransactionStatus status
) {
}


Java automatically generates implementations of:
- toString()
- equals()
- hashCode()
That means records already provide value-based equality using their components.

Regular classes don't automatically get that behavior. You decide what equality means for them.
